# 设计任务书

## 做什么
把业主的零散诉求翻译成一份可勾选、可验收的功能任务书：明确空间清单与面积指标、预算口径与设计标准、验收标准与决策人。S6 定稿时再用同一份任务书逐条回核，确认定稿没有偏离最初需求。

**启动方式取决于业主给了什么**：只有一句话就开访谈；已有图纸就先读再问；资料齐了就直接成稿。
问题按项目类型不同（住宅问家庭结构，办公问组织结构，酒店问客群与后勤），
而且「资料齐了」不等于「可以出图」——精度是另一件事。详见 `docs/S1_INTAKE.md`。

## 什么时候用 / 不用
| 用 | 不用 |
|---|---|
| 业主要求"先给我一份功能任务书 / 面积表" | 判定结构安全、消防或无障碍是否达标 |
| 需求访谈后要把口头诉求固化成可验收条目 | 出正式工程量清单或结算依据 |
| 要区分"必须项 / 加分项 / 可放弃项" | 替业主决定风格取向与审美 |
| S6 定稿前用任务书逐条回核 | 替代造价咨询的报价工作 |

## 输入 → 输出
| 输入 | 输出 |
|---|---|
| 业主访谈记录、需求清单 | `design-brief.md` — 功能任务书（空间清单 + 面积指标 + 约束） |
| 预算区间与目标入住时间 | `program.json` — 结构化空间与面积条目（含公摊口径） |
| 场地与原始建筑条件 | `brief-checklist.md` — 验收标准与决策人清单 |
| 面向对象（居住 / 办公 / 商业 / 酒店） | `uncertain-items.json` — 标 `uncertain = true` 的待澄清项 |
| 参考案例或风格倾向 | `design-brief-r{n}.pptx` — 任务书确认汇报（G1 材料） |
| 业主首句需求（可能只有一句） | `user-needs.json` — 使用行为矩阵（活动 / 人数 / 频率 / 隐私） |
| 已上传图纸 / 照片 / 原任务书 | `feasibility-report.md`、`design-opportunities.md`、`uncertainty-register.json` |

## 操作步骤
1. 先判启动情形（一句话 / 有资料 / 资料齐），再决定问什么、读什么：
   `python -m omniarchitect intake --project P --action start --text "..."`。
2. 访谈每轮只问 1–3 个最关键的问题；首句已说过的面积、城市、人数、风格不再重复问。
3. 按"必要—加分—可放弃"三档归类需求，逐条问清用途、人数、时段与使用频率。
4. 把每条需求映射成一个或一类房间，给出净面积预估并标注是否含公摊。
5. 明确预算口径（是否含软装、机电、税费）与设计标准档次，写成一句可引用的话。
6. 列出验收标准：每项需求对应什么可观察、可测量的完成状态。
7. 跑 `--action analyze` 生成成果包，再以 `--action gate` 提交 G1；有阻断级问题时不得直接通过。
5. 逐条核对矛盾（如"大书房 + 小预算""开放厨房 + 中式重油"），暴露并给出取舍建议。
6. 把信息缺失、需现场核对、需业主拍板的条目汇总为未决项清单，逐条指定决策人。
7. 出具 `design-brief-r{n}` 供 G1 门禁确认。

## 判断清单（可判定的判据）
| 判据 | 判准 |
|---|---|
| 需求映射完整度 | 任务书每条需求都能映射到具体房间，无"为了填满平面"的冗余空间 |
| 面积口径 | 明示含 / 不含公摊；各房间净面积合计与目标建筑面积偏差 ≤5%（常见工程惯例区间） |
| 预算口径 | 写明是否含软装、机电、税费；未写明即视为未通过 |
| 未决项 | 提交前未决项要么清零，要么逐条指定决策人（不可隐去） |
| 验收标准可判定 | 每条验收标准含可观察完成状态，禁用"高级""大气"等形容词 |
| 决策人明确 | 每个待拍板项写出唯一决策人，不写"业主们" |

## 硬性规则
0. **不虚构**：面积、预算、结构条件、法规条款都没有依据时一律标 `unknown`，
   不填占位值、不猜"业主大概想要"。每条信息只有五种状态：
   `verified` / `documented` / `inferred` / `unknown` / `conflicting`。
1. **不代业主决策**：给推荐 + 理由 + 备选，不写"几套都行"。
2. **不把估算当结算依据**：任务书中的面积与预算为方案阶段口径，不构成结算依据。
3. 需求矛盾必须暴露并给出取舍，不得自行删改业主诉求后当作已解决。
4. 结构安全、消防、无障碍、机电负荷与当地法规符合性不在本能力结论范围内，须由持证专业人员在项目所在地复核签署。
5. 信息不完整时写 `uncertain = true` 并进校核阻断项，不得用假设数字填满任务书。
6. 平台未接入时只交付任务包并标 `awaiting_platform`，绝不写占位内容、绝不改道第三方。

## 常见坑
| 坑 | 后果 | 怎么避 |
|---|---|---|
| 只记需求不记用途与频率 | 面积拍脑袋，后期大改 | 每条需求追问用途、人数、时段 |
| 预算口径不写清 | 到定稿才发现超预算 | 任务书阶段锁死含 / 不含项 |
| 把加分项写成必须项 | 造价失控 | 三档归类并请业主书面确认 |
| 未决项口头约定不留档 | 下游返工无人认账 | 未决项清单化并指定决策人 |

## 与阶段 / 其他能力的关系
- 参与阶段：S1, S6
- 上游能力：`site-analysis`（场地与建筑条件）、`existing-drawing-analysis`（原始图纸）
- 下游能力：`concept-design`（概念方向）、`space-planning`（平面落位）、`cost-check`（预算适配）
- 本能力的产物进入：G1 任务书确认材料、S6 定稿回核依据
