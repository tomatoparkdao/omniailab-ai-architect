# 设计汇报与提案

## 做什么
设计汇报与提案把该阶段的专业成果转译为**可决策**的提案：让业主在有限时间内看清方向、看懂取舍、做出确认。它是跨阶段通用能力——每个阶段都产出对应深度的汇报文件，而不是只在最后做一次。每份汇报都必须含**免责与边界页**，效果图类页面必须声明非尺寸依据。品牌样式可自定义 `Brand`（名称、主色、纸色、字体、页脚）。

## 什么时候用 / 不用
| 用 | 不用 |
|---|---|
| 业主要求"先给我两套平面比一比"（S3 比选） | 生成设计内容或校核设计是否达标（由各设计能力负责） |
| 阶段成果需要向业主确认、锁定或交底 | 判定结构、消防、无障碍、机电负荷是否合规 |
| 需要把模型/工程量/校核结果组织成一套讲述 | 用效果图作为施工尺寸依据或验收依据 |
| 概念效果图（S3 门禁后）需要成页呈现空间感受 | 引用第三方事务所作品充当本项目案例 |
| 全过程需要一个可复述的汇报簇（`full`） | 以汇报结论替代持证专业人员的复核签署 |

## 输入 → 输出
| 输入 | 输出 |
|---|---|
| 统一空间模型（Canonical Spatial Model）当前修订 | `presentation-<kind>-r<revision>.pptx` — 可编辑 PPTX |
| 该阶段成果：概念/平面与指标/材料与照明/图纸/工程量与估算 | `presentation-<kind>-r<revision>.md` — 文字版，便于评审与检索 |
| 评审与校核结果（含待确认项与阻断项） | `presentation-<kind>-r<revision>.html` — 打印就绪版式（浏览器可另存为 PDF） |
| 可用媒体资产（示意图/效果图/意向图）及其 provider 与任务 ID | `presentation-<kind>-r<revision>.pdf` — **仅当本机存在真实渲染器时**生成 |
| 品牌样式（`Brand`：名称、主色、纸色、字体、页脚） | `presentation-<kind>-r<revision>.deck.json` — 汇报数据模型 + 产出清单 + 内容来源 |

汇报类型（kind）共 **10 种**，按阶段取用：

| kind | 阶段 | 用途 |
|---|---|---|
| `concept` | S2 | 概念设计提案：立场、原型、关键词、意向板 |
| `plan-comparison` | S3 | 平面方案比选：可比指标 + 面积配比 + 造价影响 |
| `concept-rendering` | S3（**G3 门禁后**） | 概念效果图：以业主确认的平面为依据，供建立空间感受 |
| `preliminary` | S4 | 初步设计汇报：顶墙地做法、立面、材料与机电协调 |
| `materials-lighting` | S4 | 材料与照明专项：材质板 + 编号 + 光效场景 |
| `visual` | S5 | 视觉表现汇报：表现图与机位说明 |
| `final` | S6 | 设计定稿确认：决策台账 + 待确认项 |
| `technical-briefing` | S7 | 施工图技术交底：图纸清单 + 协调接口 |
| `delivery` | S8 | 交付与物料清单说明 |
| `full` | 全过程 | 各阶段页组合的完整汇报簇 |

## 操作步骤
1. 读取模型当前修订，确定汇报深度（kind）与目标读者（业主/评审/施工方），对受众分层调整详略与术语。
2. 按 `DeckBuilder` 组织页面：封面 → 结构 → 项目摘要 → 概念/平面/材料/照明/表现 → 决策 → 预算 → 协调 → 图纸 → 待确认 → 下一步 → **免责与边界**。
3. 每一页数据都必须来自模型、工程量或校核结果；缺失时写明"尚未生成"，**不得用占位数据冒充结果**。
4. 生成页面时记录 `provenance`（本次用到哪些知识域与数据源），保证数字口径唯一、可追溯。
5. 生成 `concept-rendering` 前确认 G3 已通过：平面未确认不得出概念效果图；平面一变，已出的概念效果图立即失效并重出。
6. 写出 PPTX / Markdown / HTML；PDF 仅在检测到真实渲染器时生成，否则不产出该格式。
7. 自检：页数下限、封面、免责与边界页、空页、表格列数一致性；未过检不得作为交付件。

## 判断清单（可判定的判据）
| 判据 | 判准 |
|---|---|
| 免责与边界页 | 每份汇报必须存在，缺页即不合格 |
| 一句话结论 | 每份汇报有 1–2 页结论，可被复述 |
| 每页信息点 | 1–3 个（常见表达惯例区间），避免过载 |
| 方案对比数 | 2–3 个（常见表达惯例区间），同标准同格式呈现 |
| 效果图页声明 | 必须声明"非权威、不得作为尺寸依据" |
| 数字口径 | 面积/造价的来源与口径统一，图面与口头一致 |
| 未决项与风险 | 显式列出并指定决策人，不隐瞒 |
| 材料版本号 | 汇报文件带版本号与日期，目录与实际页一致 |
| 安全与合规内容 | 一律标注"待持证专业人员复核签署" |

## 硬性规则
1. **必须包含免责与边界页**：结构安全、消防、无障碍、机电负荷与法规符合性不在系统结论范围内，须由持证专业人员复核签署。
2. **效果图不得作为施工尺寸依据**：表现页必须声明该图非权威成果；`concept-rendering` 只能在业主确认的平面上生成。
3. **不得引用第三方事务所的自有作品**作为默认汇报案例；案例只能来自原创知识库与用户授权内容。
4. **不得凭空声称具备 PowerPoint MCP**；PPTX 只能由已验证的写出后端（`python-pptx` 或内置 OOXML 兜底）产生，并**回报所用后端**；写出后须用独立实现重新打开校验（part 完整性、slide 数量、文本可读）。
5. **不代业主决策**：给推荐 + 理由 + 备选，不写"两套都行"。
6. **深度如实**：预算与工程量标注为方案阶段估算，不构成结算依据；示意图 ≠ 效果图，方案深度 ≠ 施工图深度。

## 常见坑
| 坑 | 后果 | 怎么避 |
|---|---|---|
| 平面未确认就出概念效果图 | 图对不上最终平面，业主预期被误导 | `concept-rendering` 挂 G3 门禁后执行，平面变即重出 |
| 汇报缺免责与边界页 | 业主误以为已通过合规审查 | 自检卡"免责页必须存在"，缺页不交付 |
| 用占位数据填空白页 | 数字失真，决策依据不可靠 | 缺失即写"尚未生成"，不虚构 |
| 声称有 PowerPoint MCP | 写出后端不真实，文件损坏 | 只用已验证后端，并回报后端名与校验结果 |
| 各阶段共用一套讲法 | 施工方看不懂或业主被细节淹没 | 按受众分层，逐 kind 调整详略 |

## 与阶段 / 其他能力的关系
- 参与阶段：`[S2, S3, S4, S5, S6, S7, S8]`（跨阶段通用）
- 上游能力：`concept-design`/`space-planning`（提供概念与平面）、`material-design`/`lighting-design`（提供材质与光效）、`quantity-takeoff`/`cost-check`（提供工程量与估算）、`design-review`（提供校核结论）
- 下游能力：业主确认推进对应门禁（G2–G8）；`delivery` 的冻结基线作为 `delivery`/`full` 汇报的唯一版本源
- 本能力的产物进入：G2–G8 各阶段确认；材料变更或平面变更时随 `delivery` 的失效重算链重出。
