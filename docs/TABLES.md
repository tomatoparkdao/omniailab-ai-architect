# Markdown 表格规范

本规范只管一件事：**GitHub 上看到的表格，左边界和右边界必须对齐。**

它看起来像排版洁癖，其实是个可判定的工程问题——下面把判别方法、换算依据和修法写清楚，
最后由 `scripts/check_tables.py` 守住，不靠人眼。

---

## 一、问题从哪来

GitHub 渲染 Markdown 表格时用的是：

```css
table { display: block; width: max-content; max-width: 100%; }
```

意思是：**表格宽度由内容撑开，源码里无法指定宽度。**（HTML 的 `width` 属性对 Markdown
表格不生效，除非把整张表改写成 HTML——那会牺牲可编辑性，本仓不采用。）

由此产生两种表现：

| 内容宽度 | 渲染结果 | 看起来 |
|---|---|---|
| 超过正文区 | 被压到 `100%`，左右都贴边 | 满宽，正常 |
| 不足正文区 | 按 `max-content` 停住 | **右边界缩进，与上一张表不齐** |

所以「表格左右不齐」不是对齐标记写错了，而是**那张表的内容不够宽**。

---

## 二、宽度怎么算：显示宽度单位

把每个字符折算成显示宽度单位：

- **中日韩字符、全角标点 → 2**
- 其余（ASCII、半角标点）→ 1

这个数字与渲染后的像素宽度成正比，可以直接拿来比较。

### 量的是「渲染后可见文字」，不是原始 Markdown

这一步最容易做错，而且错了不会报错、只会漏检：

| 写法 | 页面上的样子 | 算多少宽度 |
|---|---|---|
| `[操作手册](https://example.org/very/long/path)` | 操作手册 | **只看「操作手册」4 个单位**，URL 一个字符都不算 |
| `**注意**` | 注意（加粗） | 4 个单位，`**` 不算 |
| `` `schematic` `` | schematic（等宽字体） | 9 个单位，反引号不算 |
| `第一行<br>第二行` | 两行 | 取两行中较宽的那一行，**不是相加** |
| `<img src="…">` | 一张图 | 不计文字宽度 |

**本仓就吃过这个亏**：「文档地图」那张表只有两列短条目，按原始 Markdown 量是 213 单位、
看起来早就够了；按可见文字量其实只有 **81** 单位，在 GitHub 上仍然比正文区短一大截。
所以 `scripts/check_tables.py` 里的 `rendered_text()` 负责剥掉链接地址、HTML 标签与强调标记，
再由 `cell_width()` 按 `<br>` 取最宽的一行。

**手工核算时也要这么做**：把链接地址去掉，只数页面上能看到的字。

### 阈值 140 的推导

| 量 | 取值 | 依据 |
|---|---|---|
| GitHub 仓库页正文区宽度 | ≈ 950 px | `container-lg` 上限 1012 px 减去内边距 |
| ASCII 平均字宽 | ≈ 8 px | 16 px 字号下的系统 UI 字体 |
| 中日韩字符宽 | ≈ 16 px | 全角，正好 2 个 ASCII |
| 换算后正文区宽度 | ≈ 119 单位 | 950 ÷ 8 |
| **本仓取用的下限** | **140 单位** | 约 18% 余量，覆盖较窄窗口与字体差异 |

**取 140 而不是 119，是为了留余量。** 表宽一旦超过正文区，浏览器就把它压到 100%，
所以「超了」没有副作用；「差一点」才会露出缩进的右边界。

## 三、五条硬规则

| 编号 | 规则 | 适用范围 | 违反后果 |
|---|---|---|---|
| **T1** | 表头、分隔行、每个数据行的列数必须一致 | 全部 Markdown | 该行被渲染成错位的碎单元格 |
| **T2** | 表中不得有空单元格 | 全部 Markdown | 空列会被压到最窄，整表变形 |
| **T3** | 分隔行统一写成紧凑形式：每段只有三个连字符，竖线紧贴，不留空格、不加对齐冒号 | 全部 Markdown | 与全仓格式不统一；`normalize_attribution` 会改回去 |
| **T4** | 每张表总显示宽度 **≥ 140** | 落地页 `README.md` / `README_EN.md` | 撑不满正文区，右边界缩进 |
| **T5** | 每张表列数 **≤ 6** | 落地页 | 列太多，每列都被压成窄条，可读性崩塌 |

> **为什么要区分落地页**：README 是别人进仓库第一眼看到的东西，排版不齐直接影响可信度；
> 而 `docs/`、`knowledge/`、`skills/` 里的表是查阅型材料，窄表反而更好扫读，不强制撑满。

分隔行的标准形态（三列表格为例，竖线紧贴、不留空格、不加对齐冒号）：

```text
|---|---|---|
```

`normalize_attribution.py` 会把任何变体（`| --- | --- |`、`|:---|:---:|---:|`）改回这一形态，
所以不要手工添加对齐冒号——那是**列内文字对齐**，与表格宽度无关。

## 四、怎么把表撑到 140：补内容，不是补空格

### 正确做法

| 手法 | 说明 | 示例 |
|---|---|---|
| 加一个信息列 | 表里缺的那一维补上，内容取自仓库既有事实 | 能力清单加「说明」列，内容取自 `skills/<能力>.md` |
| 把现有列写足 | 短标签扩成完整表述，把省略的判断补回来 | 门禁列 `G3 平面方案确认` → `G3 平面方案确认（业主 / 主创）` |
| 加「落点 / 依据」列 | 写清这条规则在代码或文档里的出处 | 概念效果图表加「落点与依据」列 |

### 禁止做法

- **禁止用空格或 `&nbsp;` 填充**：Markdown 折叠空白，`&nbsp;` 会污染正文、破坏复制粘贴，
  而且解决不了「内容真的不够」这个根本问题。
- **禁止编造内容凑宽度**：表宽是结果，不是目的。写不出第五列，说明这张表本来就该是窄表，
  应当**改写成列表或段落**，而不是塞废话。
- **禁止把整表改写成 HTML `<table width="100%">`**：会失去 Markdown 可编辑性，
  也让 diff 变得不可读。
- **禁止加对齐冒号**（`:---:`）来"凑齐"：那是列内文字对齐，与表宽无关（见 T3）。

### 反过来：太宽的表怎么办

单张表内容超过正文区很多（如本仓「七个层面」表），渲染后会被压到 100% 并在单元格内换行，
这**不违反 T4**——它已经满宽了。但若某一列宽到把其余列挤成窄条，应把长文移出表格：

> 表格放**可比较的短判据**，长论述写在表下的正文段落里。

## 五、检查与守卫

```bash
python scripts/check_tables.py            # 报告全部违规（含每张表的总宽与列宽）
python scripts/check_tables.py --check    # 有违规则退出码 1
python scripts/check_tables.py --all      # 连非落地页也按 T4 检查
python scripts/check_tables.py --json     # 机器可读
```

守卫位置：

| 位置 | 作用 |
|---|---|
| `omniarchitect/tests/test_integration.py::test_every_table_follows_the_table_spec` | 每次跑测试都会拦下违规 |
| `scripts/verify_all.py` 第 8 段之后 | 全量验收时一并检查 |

检查器跳过 `out/`（运行时产物）与 `projects/`（用户项目数据）——它们不是本仓文档。

## 六、常见错误对照

| 现象 | 真实原因 | 修法 |
|---|---|---|
| 表格右边缩进一大截 | 内容宽度不足 140 | 按第四节补真实内容 |
| 以为够宽、实际仍窄 | 量宽时把链接 URL 也算进去了（按原始 Markdown 量） | 按第二节去掉地址再量，或直接跑 `check_tables.py` |
| 只有一列特别窄，其余很宽 | 该列内容普遍很短 | 要么合并该列，要么把这一维写成完整表述 |
| 某一行整体错位 | 该行少写或多写了一个 `\|` | 按 T1 修列数 |
| 表格里出现空方块 | 单元格留空 | 按 T2 补内容；确实无内容就写「—」并说明 |
| 改了分隔行又被改回去 | `normalize_attribution` 统一为紧凑写法 | 不要加对齐冒号（T3） |

## 七、与其余格式规范的关系

| 规范 | 负责什么 | 落点 |
|---|---|---|
| `normalize_attribution.py` | 开头 front-matter、结尾署名、表格分隔行写法 | `scripts/normalize_attribution.py` |
| 本规范 | 表格结构与宽度（左右对齐） | `docs/TABLES.md` + `scripts/check_tables.py` |
| `docs/DESIGN_CRITERIA.md` | 设计判据口径 | 与格式无关 |

两者互不重叠：前者管「文件外壳」，本规范管「表格本体」。
