# 项目视觉规范：`视觉.md`

风格库回答"这套设计是什么风格"，这份文件回答"**这个项目的图，长什么样才算对**"。
前者是内容，后者是表达。两者并存，谁也不替代谁。

它是一份**项目级**文件，落在 `<project>/视觉.md`，与 `project.json` 同级，跟着模型修订走。

## 一、为什么需要它

没有它的时候，每个阶段都在重新猜"客户喜欢什么"：S2 出的意向板是一套配色，S5 的效果图
是另一套，S8 的交付册又是第三套。客户说"这套排版太普通"，系统只能改这一次，下一次
从零开始。

有了它，客户的偏好只表达一次，之后每一张图、每一页版式都从同一处读规则。

## 二、三个时机

| 阶段 | 做什么 | 不做什么 |
|---|---|---|
| **S1** | 主动问一次：有没有喜欢的设计案例、作品集、排版样本 | 不阻断流程；客户没有就按风格库推进 |
| **S2** | 有参考就解析；没有就用风格库 **+** 专业默认值合成一份 | 不为等参考文件停下概念设计 |
| **S3–S8** | 识别"排版太普通""要像这个作品集"这类话，更新规范 | 不改设计内容，只改表达 |

S1 的问题已接进问诊：槽位 `visual_refs`，优先级 `deferrable`，**不是关键项**——
一条"没有参考"的回答不会影响任务书能否成立。

引导语由 `visualref.guide()` 给出，其中包含自有素材库入口（地址唯一来源是
`omniarchitect/paths.py` 的 `REFERENCE_LIBRARY_URL`）。

## 三、能读什么，读不到什么

| 形态 | 拿到什么 | 拿不到 |
|---|---|---|
| Markdown / TXT | 全文、明确写下的规则、禁止项、颜色词 | — |
| PDF | 逐页文字、页数 | 扫描件没有文字层时一切内容 |
| PPTX | 逐页文字、页面比例 | 纯图片页的内容 |
| DOCX | 正文文字（标准库解包，不依赖第三方） | 样式表里的字号与栅格 |
| 图片 / 截图 | 画幅、主色、纸色、墨色、留白占比、对比度 | 页边距、字号、栅格列数 |
| 链接文件 | 只登记，不抓站点 | 页面内容 |

**这是能力清单，也是纪律。** 一份纯文字的参考，只能提取文字结构与审美要求；不能因为
"看起来像作品集"就编出它的图片排布。一张照片只有画面，没有版心。

`sources.probe()` 对读不到的文件返回 `ok=False` 与具体原因（缺依赖、无文字层、
不支持格式），`视觉.md` 的参考清单里如实列出。

## 四、提取的是规则，不是形容词

「高级」「极简」「有质感」不进规范。进规范的是能被指认的东西：

| 参考里写的 | 写成规则 |
|---|---|
| 大留白，图占页面 60% | `whitespace: 0.50`、`image_dominant: true` |
| 标题用宋体，正文用无衬线 | `serif_titles: true`（**只看"标题"那一句**） |
| 三栏网格 | `columns: 3` |
| 图注编号，字号很小 | `numbered_captions: true` |
| 全篇黑白灰加一点墨绿 | `paper/ink` 取参考图两端，`accent` 取高饱和色 |
| 不要彩色渐变 / 不要圆角卡片 | 进 `banned`，在提案与检查表里逐条对照 |

中文不会说"细线"，会说"线再细一点"。所以除了词表，还有一组正则处理程度式说法
（`留白再多一些` → 0.52、`图要更大` → image_dominant、`线再细一点` → 0.85）。

**图片只提供两个端点与一个占比**：纸色取亮度 P88、墨色取 P12、留白取落在纸色亮度带内
的像素占比。照片不是版面——一张天空占一半的建筑照，不会得出"版面留白 50%"，也不会
把页面染成天空蓝；纸色由参考图的冷暖做极小幅度微调（±5 个色阶），真正的底色由客户
原话或专业默认值决定。

## 五、三类来源，分开标注

每条规则都带 `provenance`：

| 值 | 含义 | 例子 |
|---|---|---|
| `client` | 客户明确说的 | "暖白纸底" |
| `reference` | 从参考文件算出来或读出来的 | 参考图暗部色、文本里的三栏 |
| `pro` | 总设计师补的 | 图注必须带归属、强调色面积上限 |

优先级：**客户原话 > 参考文件 > 专业建议**。`pro` 不是"我猜你喜欢"，是"这一项没人定，
按惯例先定，客户可以推翻"——所以它不会被写成客户要求。

## 六、文件结构

12 节，第 0 节是机读块：

```
# 视觉规范 · <项目>
> 说明
## 0 机读规则（```json visual-rules ... ```）
## 1 项目基本信息
## 2 客户审美诉求与禁止项
## 3 参考文件清单
## 4 空间审美提取
## 5 排版规则提取
## 6 风格、色彩、字体与材质
## 7 分专业图解要求
## 8 体块、轴测、剖面与分析图
## 9 图片与效果图
## 10 各交付渠道的适配
## 11 视觉质量检查
## 12 来源、版本与变更
```

程序只读第 0 节的 JSON（`brief.load()`），人来读其余章节。同一份文件，不会出现
"文档写一套、程序跑另一套"。

## 七、怎么被真正调用

| 环节 | 读取方式 | 受影响的东西 |
|---|---|---|
| 概念图解 | `diagrams.apply_theme(theme)` | 纸色、墨色、线色、强调色、线宽系数 |
| 意向板 | 同上（走 `diagrams.Svg`） | 板底色、文字色、分隔线 |
| 客户提案 | `presentation/html.py::read_theme()` → CSS 变量覆盖 | 配色、标题字族；**不动栅格与字号** |
| PPTX / 飞书 / Notion | 与 HTML 同一套 tokens | 只做排版能力差异的适配 |

`theme()` 在文件不存在时返回默认值，与上一版实现完全一致——**没有规范的项目不会因为
这套能力而变差**。

## 八、怎么改

```bash
# S1：客户还没给参考
python -m omniarchitect visual --action guide --lead architecture

# 生成（客户给了参考目录）
python -m omniarchitect visual --project projects/x --action build --refs projects/x/references

# 查看
python -m omniarchitect visual --project projects/x --action show

# 客户改口味
python -m omniarchitect visual --project projects/x --action update \
  --text "这套排版太普通了，图要更大，线再细一点"

# 判断一句话是不是视觉偏好变更
python -m omniarchitect visual --action detect --text "我更喜欢这个作品集的排版"
```

`update` 只写这句话里**真的说到**的规则。客户只说"线细一点"，纸色墨色不会被重置——
早期实现调了一次包含默认值全集的合并函数，结果客户改三次口味，整份规范就被抹成默认值。

## 九、边界

- **不替代风格库。** 风格仍由 `knowledge/styles/` 的 47 份记录与 `style/` 的推荐、配方、
  提示词编译决定；`视觉.md` 只管表达参数。
- **不改 S1–S8。** 它不新增阶段、不新增审批、不改变门禁。
- **不搬第三方资产。** 拿到参考文件不等于获得再分发权。素材库条目的使用边界见
  `docs/REFERENCE_SOURCES.md` 第 3.1 节。
- **不把配色当版式。** 客户说"换个颜色"，只改颜色；客户说"排版太普通"，才动版式。
  `theme_css()` 刻意只输出 CSS 变量，不输出栅格与字号——那是内容决定的事。
- **不做无依据的推断。** 纯文字参考不给色彩结论，照片参考不给版心结论。

## 十、检查清单

- [ ] S1 问过参考文件，且没有阻断流程
- [ ] 参考文件逐个 `probe`，不可读的写明原因
- [ ] 每条规则有 `provenance`，`pro` 未被写成客户要求
- [ ] 纯文字参考没有产生图片类结论
- [ ] `视觉.md` 的机读块能被 `load()` 读回
- [ ] 概念图解、意向板、提案三处确实读到了同一份 tokens
- [ ] 没有规范文件的项目，产出与上一版一致
- [ ] 客户变更后，`concept-options.json` 未被改动
- [ ] 变更记录里有时间、动作与一句话说明
