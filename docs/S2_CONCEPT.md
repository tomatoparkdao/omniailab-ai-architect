# S2 概念方案设计（Concept Design Engine）

S2 原来的实现写死了两个住宅策略——「中部服务脊」和「南北动静横分」——再加一句风格名。
办公项目拿到的也是这两句，酒店项目也是。业主说一句「现代意式极简」，系统就把它当成概念做完了。

这一轮把 S2 做成真正的概念设计过程，核心是拆开一件常被混为一谈的事：

> **概念方向 ≠ 设计风格。**
> 空间原型决定房间怎么组织、人怎么走、光怎么进来；风格决定它看起来像什么。
> 同一个「中部服务脊」可以是意式极简，也可以是非洲当代；
> 同一个「意式极简」既可以做动静横分，也可以做回游环。

所以本轮的输出是：**若干套空间策略不同的方向 × 每套配一套视觉语言**，不是若干张换色的图。

## 一、三个入口，一个引擎

| 入口 | 实际做的事 |
|---|---|
| `run --stage S2` | `StageRunner.stage_S2` → `concept.generate_bundle()` |
| `concept --action generate` | 直接调 `concept.generate_bundle()` |
| `concept --action deck` | 只补出提案，不改方案 |

`stage_S2` 不再生成任何自有内容，只是适配层（与 S1 同样的纪律：一个生成器）。

## 二、先读 S1，再谈设计

`concept/context.py` 把 S1 读成一个可推理的结构，每一条都带出处：

| 读什么 | 从哪读 | 用途 |
|---|---|---|
| G1 是否确认、是哪个版本、现在还是不是同一份 | `check_baseline()` | 未确认只能出探索稿；基准变了必须重做 |
| 已确认的需求与使用行为 | 需求矩阵 + 访谈答案 | 判断面积压力、隐私冲突、收纳缺口 |
| 设计机会 | `find_opportunities()` | 每套方向必须说明回应了哪几条 |
| 不确定项 | `uncertainty_register()` | 哪些限制会跟着概念走到 S3 |
| 资料精度 | `precision_level()` | 决定能不能声称"按尺寸成立" |

精度三级：`diagnostic`（无几何）/ `schematic`（有几何或图纸）/ `authoritative_capable`（有实测）。
**只有第三级才允许说"概念已按实测尺寸讨论"**，前两级在文档里明写"不按比例"。

## 三、空间原型库：22 个原型，按项目类型分

`concept/prototypes.py` 给六类项目各一套：

| 项目类型 | 原型 | 空间家族 |
|---|---|---|
| 住宅 | 中部服务脊 / 动静横分 / 回游环 / 层次入户 / 采光脊 / 复合可变核心 | 线性 / 环 / 递进 / 大厅 / 组团 |
| 办公 | 邻里组团 / 专注脊 + 协作岛 / 活动带 / 服务前置 | 组团 / 线性 / 递进 |
| 酒店民宿 | 序列式到达 / 院落组团 / 后勤脊分离 | 线性 / 院落 / 递进 |
| 餐饮商业 | 明档剧场 / 环形店铺动线 / 时段分区 | 大厅 / 环 / 递进 |
| 展厅文化 | 叙事漫步 / 黑盒白盒并置 / 岛式自由参观 | 线性 / 组团 |
| 新建建筑 | 合院式 / 板楼 + 裙房 / 体量拆分 | 院落 / 递进 / 组团 |

每个原型都写清：空间逻辑、动线、采光、分区、体验、造价影响、维护影响、技术风险、
回应哪类问题、能不能被现有平面算法直接落地。

**这一库现在只作兜底。** 有专业推敲策略的项目（建筑／室内／景观主导）走下一节，
输出标 `source="deliberated"`；回退到原型时标 `source="prototype"`，不冒充推敲结果。

## 三之二、设计推敲层：从「挑一个原型」到「推敲出一个策略」

原型有三个上限：按项目类型分组而不按主导专业、正文是固定句子、没有景观这一类。
`concept/deliberation.py` 补的正是这三处：

| 主导专业 | 策略 | 组织逻辑（logic_key） |
|---|---|---|
| 建筑（住宅／新建建筑） | 院中取院 / 逐层退台 / 架空的水院 / 双翼夹院 | 围合取院 / 剖面收进 / 地面释放 / 双翼加院 |
| 室内（住宅既有） | 一条服务脊 / 中心体块回游 / 明暗两段 / 房间里的房间 | 服务脊 / 回游核心 / 光序列 / 盒中之盒 |
| 景观 | 一池静水 / 旱溪台地 / 林下茶席 | 静水环游 / 旱溪台地 / 林下茶席 |

每条策略必须给出：parti（能画成一根线的组织逻辑）、体量与剖面、界面虚实、
六问答案（机会／理由／体验／光视比例材料／三专业整合／技术协同）、前提、代价、
在图上怎么核验。**组织逻辑互斥**是硬约束：同族或同 logic_key 的第二条直接跳过，
宁可只出两套，也不给两个换了措辞的同款。

`plan_strategy` 只有一种合法填法：平面算法真的实现了同一套组织逻辑。
目前只有「一条服务脊」= `spine_centre`。其余策略留空，S3 会如实标
`plan_strategy_supported=False`，G3 不允许把近似平面当作概念落地。

## 四、方向生成：三条硬规则

1. **按证据选，不按数量凑。** 先算信号（采光不足 / 穿越冲突 / 面积紧张 / 收纳缺口 /
   后场效率 / 访客动线 …），再用信号给策略打分。一个什么都不回应的策略不进入候选。
2. **组织逻辑必须不同。** 两套方案都是线性组织、只是走廊宽一点，那不是两个方向，
   是一个方向的两个版本。家族用尽时宁可只出两套。
3. **角色只是策略框架。** 走原型时 A 稳妥、B 特色、C 平衡；走推敲时 A/B/C 表示
   **证据强弱**（首推／对照／补充），因为推敲策略不是按"取向"分的。

## 五、审美判据：什么时候该用「克制」

原来那几条——冷调打底、暖材 ≤40%、黑 3–8%、全项目 60-30-10——是住宅极简的经验，
不是普适规律。用在度假民宿、主题餐饮、非洲当代上会把设计意图压没。

现在每条判据都有**适用条件**（风格标签 + 项目类型），并逐条给出"不适用 + 为什么"：

| 判据 | 适用 | 不适用 |
|---|---|---|
| 克制美学（冷调打底、一条主导线） | 住宅 / 办公 + minimal 类风格 | 暖调、手作、古典、浓烈类风格 |
| 暖材 ≤40% | 住宅 / 办公 + 克制类 | 酒店 / 餐饮 / 商业（暖色是产品的一部分） |
| 黑色 3–8% | 住宅 / 办公 | 明亮类风格；风格自己声明上限时按声明放宽 |
| 60-30-10 | 风格未声明色量时 | 风格库已声明自身分配时，以声明为准 |

两个实现细节值得记住：

* **「暖材」按材料词判断，不按色相。** 意式极简的墙面是暖白（色相暖、明度 0.89），
  它是打底不是暖材；只认「木 / 皮革 / 藤 / 织物 / 黄铜」这类材料词，算出来 30% ≤ 40%。
  第一版按色相算，得出 100%，直接把最典型的克制案例判成不合格。
* **风格自己声明了分配，就按它的。** 意式极简声明 40/25/20/10/5，硬套 60-30-10 必然失败，
  那说明这条判据在这里不适用，不是方案错了。

## 六、概念图解：确定性 SVG

图由数据算出坐标，纯文本 SVG，可被 XML 解析校验，可直接进浏览器与提案。

图种跟着**主导专业**分配，不跟项目类型走——三层别墅的项目类型仍是住宅，但它需要
体量与剖面，而不是五张房间关系图。

| 图种 | 表达什么 | 用在 |
|---|---|---|
| `massing` 体量演变 | 四联等距轴测：做满 → 减去 → 加入场地 → 结果 | 建筑主导 |
| `section` 剖面与楼层 | 剖切楼板与墙体、院井通高、光从哪来、人体尺度 | 建筑主导 |
| `axon` 室内剖切轴测 | 切掉两面墙的盒子：家具、界面、光斑、视线 | 室内主导 |
| `landscape` 景观总平面 | 建筑轮廓、硬质铺装、绿地、乔灌木冠幅、水景、园路、指北、比例条、图例 | 景观主导 |
| `functional` 功能关系 | 节点是真实房间/需求活动，连线是主要联系与服务供给 | 有房间数据时 |
| `zoning` 分区 | 按空间家族换形状：线性横带、递进嵌套、组团网格、环形核心、院落中空 | 有房间数据时 |
| `circulation` 动线 | 线性直行、递进折线、环形闭合、院落绕院、组团主干 + 分支 | 有房间数据时 |
| `daylight` 采光 | 外墙侧 + 三段光深示意（明写"不代表实测照度"） | 有房间数据时 |
| `sequence` 序列 | 从进门到最私密处的四段 | 各专业 |

三条硬要求：

1. **体量必须有第三维。** 等距投影在 `concept/iso.py`，三面分档明暗 + 阴影 + 画家
   算法排序。只有矩形拼贴的"体量图"不成立——它读不出哪面朝街、哪层退进去。
2. **景观图必须有图面层次。** 底（草）→ 建筑与铺装（硬）→ 水（软而深）→ 种植
   （三种冠幅）→ 路径（双线带缘）→ 标注与指北。少一层就塌成色块。
3. **园的路径不许穿水。** 这是上一版最刺眼的错，画出来就得改。

没有几何数据时图表达关系，图上明写"非按比例"；不给放线、标高与面积。

空间意向（客户一眼看到的"这套方向长什么样"）**不靠这些图**，而是来自
`research/library.py` 的素材库取图，见 `docs/VISUAL_AUDIT.md` 与 `docs/REFERENCE_SOURCES.md`。

## 七、Moodboard：色板是真的

六格协议（主空间意象 / 色彩与比例 / 材料与质感 / 空间氛围 / 家具语言 / 照明方向），
内容全部取自风格库真实记录：

* 色值与占比来自 `color_palette.hex` 与 `usage` 里声明的百分比；
* 材料来自 `materials[]`，写清用在哪、什么做法；
* 气质与排除项来自 `tags` 与 `negative_constraints`；
* 光来自 `lighting_strategy.principles` 与原型自身的采光策略。

产出 `mb-<concept>.svg`（色带 + 材料样板 + 四格文字）与同名 `.md`。
**氛围摄影图不在这里画**——那需要 AI 生成，属另一类成果，状态单独登记。

## 八、概念视觉：S2 与 G3 后不是一回事

| | S2 概念视觉 | G3 后概念效果图 |
|---|---|---|
| 依据 | 概念主张 + 风格库 | **已确认的平面** |
| 目的 | 定方向、谈氛围 | 让业主看到自己家的空间 |
| 含真实几何 | 否 | 是（机位、视高、材料取自模型） |

提交链路完全复用 `providers` 注册表：探测 → 选择 → 授权 → 提交 → 轮询 → 取回 →
格式检查 → 资产登记。没有第二套 HTTP 客户端，也不猜平台路径与模型名。

**三道锁同时打开才提交**，缺一条就停在任务包：

| 锁 | 要求 | 没打开时的状态 |
|---|---|---|
| 平台可用 | provider 已配置且声明 `image_generation` | `awaiting_platform` |
| 双开关 | `submit=True` **且** `authorize=True` | `awaiting_platform`，说明缺哪个开关 |
| 费用可知 | 平台契约声明了计价，且未超 `--max-cost` | `awaiting_cost_confirmation` |

* 只给 `--authorize` 不会提交；只给 `--submit` 也不会；
* 没有计价声明时**不猜价格**：即使给了上限也不提交，并明说"无法证明该上限成立"；
* 有计价时按 `--max-cost` 逐条累计，超上限即停止；
* 取回后校验扩展名与体积，非图片或过小一律剔除并记入 warnings。

## 九、重复运行不重复付费

每次提交前查 `concept-visual-ledger.json`（按 `job_key` = 编译后提示词 + 一致性指纹 +
修订号哈希）。同一个 key 已生成过就**复用结果**，不再发起请求：

| 台账状态 | 重跑时 |
|---|---|
| `generated` 且文件存在 | 直接复用，计入 `reused`，不产生费用 |
| `submitted`（发出去了但没等到结果） | 拦下，提示先向平台核实，不重复提交 |
| `failed`（平台报失败、无产物） | 允许重试 |

台账在提交**之前**写入，中途崩溃也不会导致下一次重付一次钱。

## 十、比较与推荐

八个维度，每项必须有理由；资料不足记「未评估」，**不折算成中间分**：

需求响应 · 机会解决 · 空间组织 · 美学与偏好 · 预算适配 · 施工与维护 · 后续深化（含未评估项覆盖度）

推荐写三件事：为什么是它、为什么不优先另外两套（并说明"什么情况下它们仍成立"）、
进 S3 前要核实什么。推荐是专业意见，**不代替业主决策**。

## 十一、G2：签的不是风格名

阻断项分两类，**只有软性的才可能被逐项接受**：

| 编号 | 性质 | 含义 |
|---|---|---|
| `G2-NO-CONCEPT` | 硬 | 还没有概念方案 |
| `G2-NO-SELECTION` | 硬 | 没有明确 concept_id |
| `G2-UNKNOWN-CONCEPT` | 硬 | 选定的编号不在本批方案里 |
| `G2-PRE-GATE` | 硬 | 这是 G1 前的探索稿 |
| `G2-BRIEF-CHANGED` | 硬 | 任务书基准已变，概念须按新任务书重做 |
| `G2-STYLE-LOCK-CONFLICT` | 软 | 已锁定风格与选定概念不一致，确认将以新概念重写锁定 |

硬性条件**不能 `--force`，也不能用文字消掉**——没有可签的东西就是没有。
软性条件必须写编号：`--acknowledge G2-STYLE-LOCK-CONFLICT`。写一段"看着像"的
描述会直接报错并列出可用编号，避免出现"用任意文本片段解除阻断"。

确认是一次**事务**，顺序固定：

1. 校验阻断项与编号；
2. 写风格锁定文件（写不出来 → 中止，什么都不签）；
3. 确认阶段状态；
4. 登记 `concept-baseline`（概念 ID、主张、空间策略、风格、材料与色彩、
   允许 S3 深化的条件、未解决风险、修订号、确认人、摘要指纹）；
5. 重建 `concept-handoff.json`；
6. 自检：锁定文件必须存在、基准概念必须等于当前选定。

第 2–6 步任一步失败则**整体回滚**到确认前（阶段状态、基准、锁定、交接一并复原），
并如实报告"未形成概念基准"。所以不存在"confirmed 但锁定文件不存在"。

`source="demo"`（`--assume-approval`）只确认状态，**不写基准**，`formal` 恒为 `False`，
不得被引用为业主签署。同一修订只有一个锁定文件；重复确认同一概念不写第二条历史，
换风格则旧锁定记入 `style_lock_history` 后覆盖。

## 十二、S3 交接：能执行，也能被反驳

`concept-handoff.json` 携带：锁定概念与 G2 基准、空间组织策略、邻接与隔离要求、
动线与采光原则、风格空间约束、待核实事项、平面策略。

S3 用它决定主策略，并在 `scheme-comparison.md` 里给出**概念一致性校核**：

| 检查 | 判定方式 |
|---|---|
| 平面策略与概念一致 | 比较 `strategy` 字段；概念无对应策略时判失败 |
| 走廊占比 | 环形/大厅 ≤18%、线性 ≤30% |
| 每间房都有采光面 | 概念要求"每个房间贴外墙"时，比对采光房间数 |
| 邻接涉及的功能存在 | 只核对任务书里真有的房间名，对不上的交人工 |

隔离类要求（访客不入私密区）**不判"通过"**，列为待人工复核——记成通过就是假通过。
因此校核结论同时给三个字段：`conformance`（自动检查）、`auto_pass`、
`fully_verified`（自动检查通过**且**没有待人工判断项）。只有 `fully_verified`
才代表"没有任何东西悬着"。

概念要求的策略现有算法不支持时，S3 用最近策略出图并明确标注
"结果不能视为概念的落地"，而不是悄悄换一个策略还说成功。

## 十三、G3：探索可以，签发不行

S3 在**没有** G2 基准时也能跑——那是探索性平面验证，完全正当。区别在签发：

| 阻断 | 触发条件 |
|---|---|
| `G3-NO-CONCEPT-BASELINE` | 没有已确认的 G2 概念基准 |
| `G3-STALE-BASELINE` | 概念基准或任务书基准在出平面之后变了 |
| `G3-NO-PLAN-RECORD` | 没有本轮的平面记录 |
| `G3-PLAN-STALE` | 平面记录不是当前修订的 |
| `G3-CONCEPT-CONFLICT` | 一致性校核为 `fail`（重大冲突） |
| `G3-PROTOTYPE-UNSUPPORTED` | 原型没有对应平面策略，本轮是通用策略的近似 |

全部是硬性条件，`--force` 与演示模式都不能把它们变成正式签发。演示模式仍可
确认阶段以让流程继续，但记录 `formal=False` 并写明"不是正式 G3 签发"。

G3 通过时把平面记录与门禁结论写进 `meta.concept.plan.gate`（正式 / 演示、
一致性、`fully_verified`、待人工复核项、阻断编号），S4 之后可追溯。

## 十四、变更回流

| 改了什么 | 结果 |
|---|---|
| G1 后改需求 | `brief_digest` 变 → G2 阻断、G3 阻断（概念与平面都失去依据） |
| G2 后换概念 | `invalidate_from("S2")` 把 S2 与下游置返工 + 写 change_log |
| 只核实了某个条件 | 限制解除，概念基准不变（不误判为需求变更） |

## 十六、边界

* 概念图解是关系表达，**不是平面图**，不得作为尺寸依据；
* S2 概念视觉不是效果图，也不是空间承诺；
* 风格锁定只约束视觉语言，不替代空间策略的确认；
* 结构、消防、无障碍、法规符合性仍须持证专业人员复核签署；
* 现有平面算法只支持 `band_day_night` 与 `spine_centre`，其余原型需专用深化——
  这一点在方案里如实标注，不用"已生成"掩盖。
