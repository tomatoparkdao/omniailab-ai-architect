# S2 多专业概念设计

## 一、概念的构成变了

旧 S2 的一套概念是：空间原型 + 风格 + 材料 + 灯光。

现在一套完整概念是：

**总体设计主张 + 建筑策略 + 结构立场 + 机电立场 + 室内概念 + 景观概念 + 多专业接口 + 成本与风险**

各部分按 S1 的专业范围启用。纯室内项目不会有"景观概念"这一节，纯景观项目也不会有"室内概念"。

## 二、不是五份互不相关的方案

这是本轮最高验收标准：**不是五个 AI 各做五份文档。**

落地方式是 `omniarchitect/concept/disciplines.py::for_concept()`：每个专业方向都从**这套概念自己的话**推导。

依据字段：

| 来源 | 用途 |
|---|---|
| `concept_statement` | 主张；建筑形体依据 |
| `spatial_prototype.spatial_logic` | 空间逻辑；室内与建筑共用 |
| `zoning` / `circulation` | 分区与动线；建筑、室内、景观共用 |
| `daylight` | 采光策略；机电与室内共用 |
| `cost_note` / `maintenance` | 成本与维护；影响结构做法与机电选型 |
| `risks` | 技术风险；结构要回答的清单 |
| `material_direction` | 材料；室内与景观共用 |

同一次推导里，四个专业变量互不独立：

```
概念「中央庭院」
  → 建筑：庭院位置定在体量中央
  → 结构：不能凭空跨过庭院（IF-STR-SPACE）
  → 室内：主要空间朝庭院开
  → 景观：庭院自己的排水与防水（IF-WATER-FR）
  → 机电：室外设备、灌溉与景观照明（IF-MEP-LAND）
全部指向同一个 concept_id
```

## 三、信号判定：概念向谁提了要求

不是每个概念都对所有专业提要求。判定靠信号表：

| 表 | 覆盖 | 命中意味着 |
|---|---|---|
| `STRUCTURE_SIGNALS` | 挑空、通高、悬挑、大跨、夹层、拆、承重、开洞、楼板、错层 | 这套概念**成立与否取决于结构条件** |
| `MEP_SIGNALS` | 机械通风、新风、湿区、立管、灌溉、照明、喷淋、水景 | 需要机电配套 |
| `LANDSCAPE_SIGNALS` | 庭院、花园、露台、屋顶、水池、中庭、绿化、室外 | 室外参与空间组织 |
| `PLANNING_SIGNALS` | 容积率、退线、限高、层数、体量、报建 | 需核对规划条件 |

命中后不是加一句形容词，而是把信号翻成**必须回答的问题**：

```
「拆」→ 要打掉的隔墙是不是承重墙、开洞限值多少
「挑空」→ 通高处能不能不落柱、允许的最大跨度是多少
「夹层」→ 新增楼层的荷载由谁承担、原基础是否够
```

没命中的写"这套概念不改变结构体系"——明确说不需要，而不是含糊地写"结构配合"。

`demanded_by` 记录触发词，`test_two_concepts_get_different_structure_demands` 守着"两套概念的结构立场不能是同一段话"。

## 四、两个状态，一眼看出能不能用

| 状态 | 含义 | 能不能当结论 |
|---|---|---|
| `proposed` | 有依据，方向成立 | 能，但仍需专业复核 |
| `requires_input` | 有要求但缺资料 | **不能**，只作为方向 |

缺资料时写条件不写结论：结构写"先鉴定后设计、需结构工程师出计算书"，不写"采用 200×500 钢梁"。

## 五、比较：缺依据的维度不评分

`compare.py` 新增四个专业维度，只评**在范围内**且**有依据**的：

| 维度 | 什么时候评 | 什么时候不评 |
|---|---|---|
| 结构可行性 | 结构方向 `proposed` | 资料不足 → `score=None`，写明"缺依据时给分等于编" |
| 机电协调难度 | 机电方向 `proposed` | 同上 |
| 景观与生态 | 景观方向 `proposed` | 同上 |
| 规划适应性 | 有报批条件 | 同上 |

范围外的专业**不加这一维**，也不给 0 分——不给分和不合格是两件事。

### 硬性前提不能被平均掉

如果某套概念自己要求结构回答，而结构还是 `requires_input`，会进 `hard_flags`：

```
**结构是这套概念成立的前提**，目前资料不足（需先明确：现有结构图纸、
要打掉的隔墙是不是承重墙、开洞限值多少）：补齐前该方案只能作为方向，
不能当作已成立方案推进
```

这条写进 `recommendation.verify_before_s3`，不会被美学分数冲淡。

## 六、G2：逐专业锁定同一份基准

风格锁定文件只管观感，管不了"结构按什么原则、景观做到什么范围"。所以 G2 另写一份 `multidisciplinary-concept-baseline-r<rev>.json`：

| 字段 | 内容 |
|---|---|
| `concept_id` / `concept_name` | 唯一概念，所有专业都属于它 |
| `active` | 本次锁定了哪些专业 |
| `not_applicable` | 明确不在范围的专业（**不等于已核对无冲突**） |
| `disciplines[]` | 逐专业：方向、目标、状态、交付物、待明确项、接口、谁签 |
| `pending_inputs` | 还是 `requires_input` 的专业与它们缺什么 |
| `interfaces` | 双方都在范围的接口清单 |

写入在 G2 事务内，顺序是：

```
写风格锁定 → 写多专业基准 → 确认阶段 → 登记基准 → 重建交接 → 自检
```

任一步失败整体回滚，磁盘文件复原。自检项包括"多专业基准文件必须存在"——所以不会出现"确认了但基准没落盘"。

### 事务一致性

不会出现"建筑方向已确认、景观概念却对应另一方案"。因为：

- 所有专业方向都挂在**同一个** `chosen` 对象上；
- 基准里逐专业写 `concept_id`；
- 范围内缺任一专业方向时，G2 直接抛错并回滚（`G2-DISCIPLINE-<id>`）。

## 七、交接给 S3

`concept-handoff.json` 新增两处：

```
gate.multidisciplinary  → 指向基准文件、active 列表、未完成项
disciplines.directions  → 逐专业的方向与接口
```

S3 起每个专业按这份对齐。`status != proposed` 的专业在交接里必带 `open_questions`——测试守着"缺资料的专业不能看起来像结论"。

## 八、还没做到的

- 结构与机电**没有执行器**：能出立场、接口与缺口量化，不能出结构计算或负荷。
- 景观没有独立平面生成器：S3 会明确阻断。
- 规划指标只做口径与缺口，不出法定结论。
- 多专业图解目前只有确定性 SVG（分区/动线/接口关系），没有建筑体量图与结构柱网图——这两项需要几何输入，本轮不伪造。
